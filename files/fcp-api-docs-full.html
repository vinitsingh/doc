FCP — Federated Commerce Protocol

HTTP/REST Binding Specification · Version 1.0.0

This document specifies the HTTP/REST binding for the FCP Checkout capability. It defines the wire format, authentication mechanisms, headers, error handling, and the complete mandate-chain security model for all checkout operations.

ℹ
FCP uses a two-phase checkout design. Phase 1 (POST /v1/checkouts) submits cart intent. Phase 2 (POST /v1/checkouts/<id>/complete) authorises and fires payment. The CartMandate is the cryptographic bridge between the two phases.

Protocol Fundamentals¶

Base URL¶

All FCP REST endpoints are relative to the merchant's base URL, which is discovered through the FCP profile at /.well-known/fcp. The exact endpoint for each capability is defined in the capabilities[].endpoint field of the merchant profile returned by the discovery operation.

Agents MUST fetch the merchant profile before initiating any session. The profile is cacheable — agents SHOULD respect the Cache-Control response header. The default cache TTL is 5 minutes if no Cache-Control header is present.

Content Types¶

  • Request: application/json
  • Response: application/json

All request and response bodies MUST be valid JSON as specified in RFC 8259. Empty bodies (e.g. for optional request bodies) MAY be omitted entirely or sent as {{}}.

Transport Security¶

All FCP REST endpoints MUST be served over HTTPS with a minimum TLS version of 1.2. TLS 1.3 is strongly recommended. Agents MUST reject connections with self-signed certificates in production environments. All requests MUST be made directly to the merchant's FCP endpoint discovered from the profile — intermediary proxies that can inspect or modify the payload are not permitted.

Authentication¶

FCP uses two complementary authentication mechanisms that operate at different levels of the stack:

  1. OAuth 2.0 — transport-level authentication. Identifies the agent to the merchant.
  2. Mandate Chain — payload-level authentication. Cryptographically proves the user authorised the transaction.

Both are required for complete. OAuth alone is sufficient for get and update.

OAuth 2.0¶

FCP uses OAuth 2.0 bearer tokens as defined in RFC 6749. All requests (except GET /.well-known/fcp) MUST include a valid bearer token in the Authorization header. Two grant types are supported:

Grant TypeUse CaseScopes
client_credentials Autonomous agent acting without a live user session (human_not_present mode) fcp.checkout
authorization_code Agent acting with an active user session (human_present mode) fcp.checkout
⚠
OAuth tokens do not prove user intent — they only prove the agent is registered. User intent is proven by the IntentMandate and CartMandate signatures. Do not rely on OAuth alone as evidence of user authorisation for payment.

Mandate Chain Authentication¶

The mandate chain proves, cryptographically, that a specific user authorised a specific agent to spend a specific amount at a specific merchant. It is submitted as part of the request payload — not as a header — so that it becomes part of the signed message body.

For create, the agent submits an IntentMandate signed by the user. For complete, the agent submits a CartMandateSigned — the merchant-issued CartMandate counter-signed by the user. See the Mandate Chain section for the full specification.

Operations¶

Discover — GET /.well-known/fcp¶

Retrieves the merchant's capability profile. This is always the first call an agent makes. The profile declares supported capabilities, available payment handlers (with their public keys for credential encryption), the loyalty programme configuration, and the merchant's DID trust anchor for mandate signature verification.

Agents MUST re-fetch the profile if it has expired per Cache-Control. Agents SHOULD not hard-code payment handler IDs — they must be read from the profile at runtime.

GET /.well-known/fcp Fetch merchant capability profile

No request body or authentication required. This endpoint is public.

Create Checkout — POST /v1/checkouts¶

Phase 1. Submits cart intent to open a new checkout session. This request contains everything about what the user wants to buy — items, buyer details, discounts, loyalty redemption, and the signed IntentMandate authorising the agent to act. It does not contain any payment information.

Upon receiving a valid create request, the merchant:

  1. Validates all line items against current inventory
  2. Computes subtotal, shipping, tax, and any applicable discounts (including loyalty redemption)
  3. Scores the request using client_context.risk signals and records the device fingerprint
  4. Issues a CartMandate — a merchant-signed document containing the session_id, exact items, and locked grand_total
  5. Returns the session with status pending_mandate

The FCP-Idempotency-Key header is MUST be included on this request. Retrying with the same key returns the existing session without creating a duplicate.

The client_context is submitted via the FCP-Client-Context header as base64url-encoded JSON on GET requests (since GET has no request body).

Update Checkout — PATCH /v1/checkouts/{session_id}¶

Modifies an active session. Only the fields provided in the request body are changed — this is a partial update (PATCH semantics), not a full replacement.

CartMandate invalidation. Any change that affects the computed price triggers the merchant to void the current CartMandate and issue a new one. The session reverts to pending_mandate status and cart_mandate_invalidated: true is returned. The agent must re-present the new CartMandate to the user for counter-signature before completing.

Cancel Checkout — POST /v1/checkouts/{session_id}/cancel¶

Terminates an active session from any pre-completion state. Cancellation triggers the following protocol teardown sequence:

  1. Mandate revocation. The CartMandate's mandate_id is added to the merchant's revocation list. Any subsequent attempt to submit this mandate in a complete request will be rejected.
  2. CP notification. The Credential Provider is notified asynchronously to void any pre-staged payment token associated with this mandate_id. The agent never held the token, but the CP may have pre-staged one; this ensures it cannot be used.
  3. Audit record. A signed CancelRecord is appended to the mandate chain, recording the reason, initiator, and timestamp. This record is immutable.

This operation is idempotent — cancelling an already-cancelled session returns 200 without error. Completed sessions cannot be cancelled; use your order management system to handle refunds.

✦
The session_id in the URL is the only required field. The request body is optional.

Idempotency¶

All state-mutating requests MUST include a FCP-Idempotency-Key header. This is particularly critical for complete, which captures payment.

  • The key MUST be a UUID v4 (RFC 4122).
  • The server MUST store the key and its response for at least 24 hours.
  • Retrying with the same key returns the cached response without executing the operation again.
  • Submitting the same key with different parameters MUST return 409 Conflict.
  • Each logical operation SHOULD use a fresh key. Do not reuse the create-checkout key for complete.
⚠
If a complete request times out or returns a network error with no response, the agent should wait and then call GET /v1/checkouts/{id} to check whether the session is completed before retrying with the same idempotency key. This prevents double-charges.

Security¶

Mandate Chain¶

The mandate chain is FCP's core security mechanism. It provides cryptographic proof that a specific user explicitly authorised a specific agent to spend a specific amount at a specific merchant. Every completed FCP transaction produces a tamper-evident three-mandate chain that serves as legally-admissible evidence for dispute resolution.

→

IntentMandate¶

A Verifiable Digital Credential (VDC) created by the Consumer Agent and signed by the user using a hardware-backed private key (e.g. device Secure Enclave or hardware security key). It captures the user's shopping intent and the constraints under which the agent is authorised to act.

The IntentMandate answers: "What did this user authorise their agent to do, and within what limits?"

CartMandate¶

The CartMandate is issued by the merchant after computing exact totals. It is the binding contract between Phase 1 and Phase 2. It contains the session_id inside the merchant's JWS signature — creating a cryptographic binding between the checkout session and the complete request.

The CartMandate answers: "What exactly did the merchant commit to deliver, and what did the user agree to pay?"

SettlementMandate¶

The SettlementMandate is issued by the merchant after verifying the full CartMandate chain. It packages the verified mandate chain into a payment instruction and sends it to the PSP alongside the payment token resolved from the Credential Provider. The Consumer Agent never sees the SettlementMandate or the payment token.

The settlement_mandate_id is returned in the CompleteResponse.settlement block and in the mandate_chain summary. This ID is the primary reference for post-purchase dispute resolution.

client_context & Risk Scoring¶

Every FCP request MUST include a client_context object carrying three groups of signals. These are not optional telemetry — they are protocol-level inputs used for fraud prevention, regulatory compliance, and risk-based payment routing.

At complete time, the merchant performs a delta check comparing the client_context received at complete against the one recorded at create:

risk.risk_score increased significantlyBehavioural risk signals changed during sessionEscalate to SCA if score exceeds merchant threshold
location.is_tor became trueClient switched to Tor exit node during sessionReject or apply highest-friction SCA

Payment Token Flow¶

FCP deliberately excludes the payment token from the complete request. The agent submits payment_handler_id as a reference only — the merchant calls the Credential Provider server-to-server using the mandate_id as a key, and the CP delivers the token directly to the PSP. This eliminates the agent as a payment credential intermediary.

  │                    │                         │                 │
  │  POST /complete    │                         │                 │
  │  { cart_mandate,   │                         │                 │
  │    handler_id,     │  resolve_payment(        │                 │
  │    confirm_total,  │    mandate_id: "cm_001", │                 │
  │    client_context} │    handler_id: "gpay",   │                 │

Real-Time Trust Engine
A behavioral trust runtime that sits above payment rails and commerce protocols — verifying that AI agents do exactly what humans authorized, on every action, in real time.
Draft v1.0  ·  Confidential
The problem

Agents are transacting autonomously. Nobody can prove they did what they were told.

The agentic commerce ecosystem is being built right now. AI agents are booking travel, purchasing software, managing procurement, and executing multi-step financial workflows — without a human present at each step. The infrastructure catching up around them answers two questions well:

Can this agent pay? — Visa TAP, Mastercard Agent Pay, and the Verifiable Intent open spec handle payment credential binding and delegation chains.

What is the agent buying and how? — OpenAI ACP and Google UCP handle structured commerce sessions, cart checkout, and merchant integration.

But nobody answers the third question — the one that makes everything else unsafe:

"Is this agent actually doing what the human authorized — and can anyone prove it, cryptographically, at this moment?"

When an agent's instructions are corrupted by a malicious webpage, when its task interpretation drifts across twenty reasoning steps, when a sub-agent is spawned with modified scope — every existing trust check passes. The credential looks valid. The payment authorises. The harm happens.

This is the gap MESH fills — not by competing with existing protocols, but by adding the one layer none of them provide: a live behavioral runtime with an intent verification engine.

The product

A runtime that guards agent behavior. An engine that verifies intent.

MESH has two inseparable components. The runtime issues and carries a signed artifact — the Agent Trust Token — through every hop of an agent's execution. The engine evaluates every proposed action against the original human intent before it executes. Together they answer two distinct questions simultaneously:

Trust

Verifiable chain of authority

Who, through a cryptographically signed delegation graph, authorized this agent to act — and is that authority still valid right now?

Intent

Verifiable statement of purpose

What exactly was this agent told to do — and has its behavior stayed consistent with those original instructions since they were signed?

Engine

Live behavioral evaluation

A semantic drift score and injection flag computed before every action. The only layer in the ecosystem that monitors agent behavior in real time, not just at credential issuance.

How MESH relates to the agent

The ATT is always created by the human. The engine always runs at the agent's output boundary.

There is one rule that holds without exception across every agent type: the agent never creates the ATT. The human defines the task and scope. MESH issues and signs the ATT before the agent starts. The agent receives the already-sealed token and carries it. An agent that self-issues its own trust token would defeat the entire purpose — it would be a contractor writing their own reference letter.

Where MESH physically sits depends on whether the agent runtime is open or closed.

MESH integrates with two parties: the deployer who builds or configures the agent, and the merchant who accepts the transaction. OpenAI, Google, and every other LLM runtime sit between those two surfaces as interchangeable infrastructure. MESH does not need them to call its API, adopt its spec, or know it exists.

The engine

What makes MESH a runtime with an engine — not just another credential format.

Every existing protocol in this space is a static credential: a signed artifact that proves authorization was granted at a point in time. MESH extends the Verifiable Intent SD-JWT format with two capabilities VI explicitly deferred — live runtime state and behavioral evaluation. These two capabilities are the engine.

MESH — what runs before every action
Prompt hash verification

SHA-256 of the agent's original instruction context, signed at task creation. Any modification to the agent's instructions after the ATT is issued — through prompt injection, context manipulation, or tool response tampering — produces a hash divergence. Detected before the action executes.

Semantic drift scoring

A lightweight LLM classifier compares every proposed action against the natural language task statement in the signed intent envelope. Returns a drift score between 0 and 1. Actions semantically inconsistent with the original task are flagged even if they technically fall within the structured scope limits.

Prompt injection detection

Tool responses, webpage content, and API returns are scanned for adversarial instruction patterns before they enter the agent's context. Detected injection attempts are logged as permanent flags on the ATT — visible to merchants, processors, and auditors even if the action was ultimately blocked.

Runtime state tracking

Live counters for actions taken, budget consumed, and verification count are maintained per ATT. Merchants and processors receive current state with every verify response — not just a point-in-time credential. Velocity anomalies (high action count, unusual spend rate) trigger automatic flags.

The engine is the reason MESH cannot be replicated by writing a spec. It accumulates behavioral data across every ATT issued and every verification run — building a proprietary understanding of what normal agentic task execution looks like versus compromised, drifted, or injected execution. That dataset is the compound moat.

The token

The Agent Trust Token — six layers in a single signed artifact.

The ATT is a ~3KB SD-JWT that travels as an HTTP header alongside every ACP or UCP session. It is self-contained — a merchant can verify it without calling MESH in the happy path. Six layers, two signatures, selective disclosure so each party sees only what it needs.

Agent Trust Token (ATT)  ·  SD-JWT  ·  EdDSA  ·  selective disclosure  ·  ~3KB on the wire
Header
JOSE header

alg: EdDSA  ·  typ: ATT+SD-JWT  ·  kid: key_id  ·  ver: 1.0

Trust
Delegation chain block

att_id  ·  principal (KYB-verified org)  ·  agent_identity (keypair + framework)  ·  delegation_chain[ ] — each hop signed, scope narrows  ·  revocation_id

Intent
Intent envelope block

task_id  ·  ~task_description (selectively disclosed — hash only to merchants)  ·  task_hash  ·  behavioral_scope { allowed_actions, categories, max_value, blocked_categories, geographies }  ·  prompt_hash (sha256 of original instruction context)  ·  constraints { requires_approval_above, no_recurring_without_approval }

Engine
Runtime state block — live, updated per verification

state (active / suspended / awaiting_approval / revoked)  ·  actions_taken  ·  budget_consumed  ·  drift_score (0–1)  ·  injection_flags[ ]  ·  last_verified_at  ·  verification_count

Refs
Protocol references block — interoperability anchors

acp_session_id  ·  ucp_session_id  ·  tap_token_ref  ·  payment_instrument_id  ·  checkout_hash (links to merchant-signed cart)

Sig
Dual signature block

issuer_sig — MESH platform, signs all layers  ·  principal_sig — enterprise private key, signs intent + delegation (MESH cannot issue unilaterally)  ·  selective_disclosures[ ] — disclosure keys per field per role

Three things are deliberately absent from the token: the raw prompt text (only its hash), the agent's internal reasoning (only its actions), and payment card numbers (only a reference pointer). The ATT is a trust document, not a payment credential.

Why both dimensions are required

The four states of an agent. The amber quadrant is the gap nobody else fills.

Trusted + verified intent

Agent is authorized AND behaving consistently with its original instructions. All six MESH checks pass. APPROVE.

Untrusted + any intent

No valid delegation chain. Spoofed or rogue agent. Every existing protocol catches this. BLOCK.

Trusted + unverified intent

Legitimate agent that has drifted or been prompt-injected mid-task. Passes every existing trust check. Only MESH catches this. FLAG. This quadrant is MESH's unique reason to exist.

Untrusted + unverified intent

Unknown actor, unknown task. No authorization chain, no intent context. BLOCK.

Integration model

Two surfaces. Deployer and merchant. LLM runtimes are infrastructure below both.

OpenAI has ACP. Google has UCP. Both are open specs that handle commerce sessions well. Neither needs to call MESH and neither will — they are LLM infrastructure, not integration targets. MESH integrates with the parties on either side of the LLM: the deployer who builds the agent-powered product, and the merchant who accepts the transaction. The LLM runtime is interchangeable.

Deployer surface — enterprises and SaaS builders

The deployer is anyone who builds or configures an agent-powered product using an LLM API. An enterprise IT team building an internal procurement bot on the Assistants API. A startup building an AI travel product on Gemini. A developer building a custom AutoGen workflow. In all three cases the deployer controls the agent configuration entirely — which tools it can call, what system prompt it receives, which SDK it runs. They integrate MESH at this layer, not at the LLM layer.

For custom agents (LangChain, AutoGen, bespoke code), the MESH SDK is imported as a dependency. The human calls att = mesh.create(task, scope) at task creation. The SDK registers as middleware. Every tool call is intercepted by the engine before executing. Full prompt visibility, strongest guarantee.

For API-based agents (Assistants API, Vertex AI, any managed agent service), the deployer configures the agent with the MESH SDK at the application layer they own — injecting the ATT into the system context and pointing tool definitions at MESH-wrapped endpoints they control. The LLM itself is unaware of MESH. The deployer is in full control.

The deployer integrates MESH because their compliance team requires auditability, their legal team requires liability documentation, or because "MESH-verified" is the answer to the CFO's "how do I trust this AI" objection in enterprise sales. The LLM runtime is irrelevant to this decision.

Merchant surface — the universal backstop

Every merchant accepting agent-initiated transactions calls POST /v1/verify before confirming any order. One endpoint. One integration. Works identically for every agent runtime, every deployment model, every LLM provider. The merchant receives a verdict — approved, blocked, or flagged — in under 100ms.

The merchant does not need to know or care whether the agent used OpenAI, Google, or a custom framework. They care about three things: is the ATT valid, is this action within the signed scope, and does the behavioral state show any drift or injection flags. MESH answers all three from a single call.

This is also where merchant adoption creates platform pull. When enough high-risk merchants require an ATT as a condition of accepting agent transactions, that requirement flows back to whoever deployed the agent — enterprises and SaaS builders — creating demand for MESH integration without any direct engagement with OpenAI or Google.

Defensibility

The credential format is commodity. The engine is the moat.

Within 18 months the basic signed delegation chain will be open infrastructure — the same way TLS became free. MESH's defensibility does not come from the credential format. It comes from four compounding advantages that cannot be replicated by publishing a spec.

01

Proprietary behavioral dataset

The drift detection engine trains on what normal agent task execution looks like versus compromised or drifted execution. This dataset accumulates with every ATT issued and every verification run. Proprietary, improves with scale, cannot be copied.

02

Two-sided network effect

Every SaaS builder integrating the SDK produces agents that carry ATTs. Every merchant integrating the verify API accepts those agents. More of each makes the network more valuable — the same flywheel that made Stripe's developer ecosystem defensible.

03

Standard-setting position

Contributing the runtime state block and engine as official VI spec extensions places MESH at the center of the emerging standard — the way Stripe.js and card tokenization became the default path developers reached for without thinking about it.

04

Rail-agnostic positioning

Visa TAP is card-rail bound. ACP is OpenAI/Stripe. UCP is Google. MESH works across every settlement method — cards, USDC, ACH, whatever comes next — because it operates above the rails, not inside them. No single network can internalize it.
